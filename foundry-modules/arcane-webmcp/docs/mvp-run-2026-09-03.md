# MVP run — 2026-09-03

## Result

The read-only architecture is viable. A Foundry VTT module loaded in the top-level `/game` document registered two Site tools, Codex's built-in Browser discovered both tools, and both direct and SDK-backed calls returned data from the current GM session.

## Environment

- Foundry VTT: 13 build 351
- D&D 5e: 5.3.3
- World: `testclean`
- Browser page: `http://localhost:30001/game`
- Module: `arcane-webmcp-mvp` 0.1.0
- SDK runtime: 0.1.0, protocol 2
- Runtime SHA-256: `827e008b48d07962d587fd0e97d8292bc454c47437c79a6f1a82e9680ad3a8fb`

## Evidence

1. Foundry listed **Arcane WebMCP MVP** in Module Management and accepted it as an enabled module.
2. The page console logged:

   ```text
   [arcane-webmcp-mvp] registered Site tools: arcane_probe, arcane_world_info
   ```

3. Codex reported exactly these tools for the active document:

   ```text
   arcane_probe
   arcane_world_info
   ```

   Both definitions had `readOnlyHint: true`, a closed empty-object input schema, origin `http://localhost:30001`, and page URL `/game`.

4. `arcane_probe` returned `ok: true`, Foundry `13.351`, D&D 5e `5.3.3`, world `testclean`, a ready GM session, and the expected SDK runtime hash.
5. `arcane_world_info` returned the same world/system/GM identity through the SDK runtime and reported the active `dae`, `midi-qol`, `socketlib`, and `times-up` modules.
6. A second page reload exposed the same two tools and `arcane_probe` succeeded again.
7. Navigating the tab from `/game` to `/robots.txt` produced no available Site tools. Returning to `/game` restored the two tools.

No blocking confirmation prompt appeared for these read-only calls. Write-tool review behavior is intentionally untested.

## Environment issues encountered

- Port 30000 was occupied by WebStorm JCEF, so Foundry was launched explicitly on port 30001. WebStorm also held the IPv4 loopback binding for 30001; `localhost` resolved to Foundry's IPv6 loopback listener while `127.0.0.1:30001` reached the unrelated process and returned an empty response.
- The existing `testclean` configuration had **Token Action HUD D&D 5e** enabled while its required **Token Action HUD Core** dependency was disabled. Foundry rejected all module-setting saves until the core dependency was enabled. The test corrected that existing local dependency mismatch as part of enabling the MVP module.

Neither issue was caused by the MVP code.

## Decision

Proceed to a P1 branch only after deciding how to remove `Function()` from the production SDK adapter. The next test should expose one reversible, write-shaped no-op or test-only setting mutation to measure confirmation UX, interruption behavior, and duplicate-call protection before exposing `executeTurn`.
