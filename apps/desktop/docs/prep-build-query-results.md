# 车卡成长查询：新假设与首轮试验

2026-09-09，执行前登记。放弃“给创建任务默认追加SRD正文skill就能改善表现”作为当前优化主线，保留历史结果，不删除知识来源。新假设：一个薄的只读查询可展开系统/合集成长数据，减少模型自己拼接JS和跨文档往返。

实验工具 [prep-build-query.cjs](../test/fixtures/prep-build-query.cjs) 输入className、level、可选raceName及rules，返回该等级累计advancement、发放条目名称/UUID、选择池、当前ScaleValue、生命骰/施法配置及种族移动。直接读取dnd5e合集，不调用Actor Studio、不修改auto pack。不提供全角色JSON，不执行升级，不推定选择池有默认答案。子职与法术位推导明确留在输出范围说明中。

两臂共用native NPC、生产查包和[新的查询skill](../test/fixtures/prep-build-query-skill/SKILL.md)，不加载SRD正文。对照17工具，以JS完成查询和创建；候选额外开放foundry_build_query，共18工具。skill明确同一数据读取算法与默认策略，只有工具可用性不同。题目仍为5级人类法师NPC/INT18/火球术/长棍，但未指定项改为沿用来源或系统默认，仅必要且无默认的选择作最少补充。旧轮耗时不直接作为本轮控制组。

预定四次：Qwen3.7-plus先JS后工具；DeepSeek灰度先工具后JS，各一对，thinking开启、180秒硬上限、120秒体验目标。两个模型使用各自独立私有profile和既有provider；不更换Qwen主基线。不重放失败，超时先停止复核。既有9项检查保留，另外观察移动速度、额外工作、实际查询与选择覆盖，但不把所有PC职业机制强加为NPC要求。不用历史NPC作答案。

实跑前只读检查通过：2014版过滤、目标等级截断、ScaleValue取4、20级Signature Spells排除、ItemGrant引用解析、人类移动30尺、查询前后Actor/Item数量不变。尚未宣称完整规则支持；当前是实验夹具，不进生产工具列表。

## 首轮结果

四次完成，既定9项均通过，没有模型超时。[结构化结果](prep-build-query-results.json)保留报告、会话、配置hash、调用与默认项观察。

| 模型 | 同skill裸JS：时间 / 调用 / 模型工具轮次 | 加查询工具：时间 / 调用 / 模型工具轮次 |
| --- | --- | --- |
| Qwen3.7-plus | 160.19秒 / 12 / 10 | 136.40秒 / 9 / 6 |
| DeepSeek灰度 | 96.26秒 / 26 / 22 | 28.89秒 / 8 / 5 |

Qwen本对耗时减少23.79秒（约15%），DeepSeek减少67.37秒（约70%）；都是各一对，不宣称稳定提速幅度或显著性。120秒内正确完成：Qwen两条均未达到，DeepSeek两条均达到。两个工具组均只调用一次foundry_build_query，返回4446字节工具结果，执行约95ms/9ms。三份指南hash与实验工具hash在四次间一致，SRD正文未注入；Qwen请求thinking开启，DeepSeek请求thinking.type=enabled且effort=high。

Qwen裸JS用了七次browser_evaluate，工具组四次另加一次查询；模型工具轮次10→6。DeepSeek裸JS用了22次browser_evaluate，包含一个未await的异步包装导致p.getIndex不是函数，以及两次读取NPC schema路径错误；工具组两次browser_evaluate另加一次查询，无工具错误。输出token减少，但不将全部节省归为思考时间，供应商延迟与内容选择没有独立控制。

## 正确性与范围观察

- Qwen的JS组落实30尺移动，工具组遗漏。工具组实际以Wizard/Human/5/2014查询，结果已含30尺，因此是采用数据的问题，不是查询缺失。
- DeepSeek两条都落实30尺。工具组创建8个条目，对照16个；没有把条目越多视为越好，核心请求满足即按原验收通过。完整职业机制不是本轮目标。
- 两个JS组没有严格遵循系统来源优先的建议，仍先查auto pack；Qwen还选择了人类变体来源。工具组固定优先系统2014来源并显示其他候选。这是工具包办来源定位带来的行为区别，但不证明所有世界的同名选择都正确。
- 不把此轮称为“全对”：未实跑施法/攻击，Qwen默认项采用仍有问题。保留原9项分数，人工观察单列。

## 本轮决定

新假设获得初步支持：两模型都减少了查询/解析往返，值得继续打磨薄查询，而非恢复默认规则正文注入。暂不进入生产，也不实现新的写入抽象。下一轮优先让返回信息清楚区分“可直接沿用的来源默认”“自动获得项”“真正需要选择的项”，验证Qwen是否采用已有的移动等信息；不通过堆更多职业条目扩大任务。随后再增加样本和迁移任务验证泛化。当前停止在本轮四次，不自动扩展迭代预算。进度见[唯一技术方案第22节](foundry-prep-play-technical-plan.md#22-转向系统成长数据的薄查询2026-09-09)。

## 评估范围修订：CR不评分

用户明确按玩家职业车卡规则评估此类任务，不评估CR数值或合理性，不因模型设置或保留CR加减分。既定9项验收原本没有CR判定，因此原通过数与耗时不变；先前把CR当作缺陷的人工意见撤回。原始快照中的CR保留作事实记录。若底层NPC数据模型依赖CR派生熟练加值，仍验收最终攻击、豁免等需要的有效数值，不要求某个CR。

后续区分两类任务而非按Actor类型决定规则完整度：从头按职业车卡，核对到目标等级的成长及默认选项；复制怪物追加职业等级，先验原怪物能力保留，再验累计职业/子职增量。HP、熟练、额外攻击等合并策略应在测试前确定，不能直接相加或事后追加标准。PC/NPC的数据结构与实现可不同，用户要求的能力语义应一致。
