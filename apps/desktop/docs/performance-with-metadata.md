# 多会话性能复核：元数据更新与连续消息

日期：2026-09-07。本次为 M8n3，在 M8m5/M8n2 产品基础上修复自动跟随滚动。完整数据见 [原始结果](performance-with-metadata.json)，旧 M8e 负载及记录保留在 [原基准](performance-baseline.md)。本次结果通过规格 §11.2 的受控响应门槛；整体平台验收仍未完成。

## 补强的负载

延续同一 Windows 设备、16 个活动任务、每会话 10,000 条历史及 5,000 条输入回执、1200×850 offscreen 窗口、每秒 160 个流片和 32 个状态事件、60 次同模式及 60 次跨模式导航。

新增每秒 16 条完整消息，写入原生 SessionManager 日志后开始下一条流式消息，触发实际 renderer 合并更新列表行。列表 IPC 现在调用生产 SessionRegistry，对每模式八个驻留会话的原生日志计算元数据；冷磁盘发现仍用缓存描述，不把本结果用于宣称首次磁盘枚举性能。记录了 285 次元数据读取，其 P95 为 18.44 ms（主进程读取阶段，非单独 UI 门槛）。

测量方式沿用首动画帧中可见正文/状态与游标同时满足的判定。流片在测量时若已结束，允许通过同身份的最终消息节点确认内容。新增完成时仍跟随最新、historyPage.hasNewer=false 的硬性断言，避免把旧页停留误计为正常实时显示。最终运行时没有并行执行本任务的其他测试，隔离 Foundry 服务已结束。

## 本次发现及修复

初次补强后，进度测量大量触发十秒超时；仅让测量器识别最终消息节点仍未通过。诊断显示 followLatest=false、historyPage.hasNewer=true，正文停在旧历史页。

原因是程序通过 scrollTop 自动滚到底部时，受 CSS scroll-behavior:smooth 影响；中间滚动位置触发监听器，将自动滚动误认为用户离开最新位置，并保存旧阅读锚点。scrollToEnd 现在明确使用 behavior:instant，自动跟随不经过会关闭跟随状态的中间位置。

长历史 Electron 验收确认主动阅读旧页、锚点、草稿附件和恢复行为保持。普通会话 fixture 原来也是赋值 scrollTop 后立刻派发 scroll 事件，实际上未等待模拟滚动到位；改为即时到达 200px，并新增离开最新位置的前置断言后通过。最终类型、源码边界和生产 metadata 回归通过；本次未修改后端状态机，未重跑全量模块测试。

复现命令：`node apps/desktop/test/benchmark-conversations.mjs apps/desktop/docs/performance-with-metadata.json`。模型供应商、真实工具耗时、系统通知/托盘、物理扫描呈现和其他设备均不属于此基准的时延承诺。
