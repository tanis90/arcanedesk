# TODO：是否提供 agent 短休 / 长休能力

状态：延期，未排期。决策日期：2026-09-07。

本轮实施范围见 [Foundry 备团与跑团工具唯一技术方案](./foundry-prep-play-technical-plan.md)。
本文仅记录待决产品问题，不是另一份实施方案，也不构成休息能力的交付承诺。

## 当前决定

备团和跑团模式均暂不实现短休/长休：不注册 foundry_rest/actor_rest，不新增内部
休息服务或 SDK action，也不在静态上下文中注入休息动作后经 foundry_execute_action
间接执行。DM 使用 Foundry 原生界面。本轮不以属性 patch 模拟休息。

## 为什么延期

- DM 在原生界面点击往往比向 agent 下指令更直接；单人休息的增益有限。
- 语音连续操作、明确批量休息、休息后资源汇总可能有价值；缺失这项能力确实留下
  全 agent 操作的缺口，但“能力闭环”本身不足以证明现在值得增加接口。
- 独立工具低频使用，却常驻工具上下文，增加定义长度与选择空间。实际延迟影响
  尚未测量，不能因为 schema 短就假定没有成本。
- 经统一执行入口提供可以减少独立工具，但仍会增加动作定义与路由语义，批量跨角色
  执行还可能扩大现有合同。暂不为了少一个工具名字而把复杂度转移进去。

## 未来需要决定

| 选项 | 收益 | 代价 |
| --- | --- | --- |
| 继续由 DM 点击 | 无新增模型上下文与执行复杂度 | 语音/全 agent 流程存在操作切换 |
| 独立 foundry_rest 工具 | 意图明确，方便批量与资源汇总 | 常驻低频工具，需衡量高频动作性能影响 |
| 作为系统动作进入静态上下文与 execute_action | 不增加独立工具名 | 增加目录/执行合同；不是角色原生 Activity，需明确路由与目标规则 |

三种选择均未选定为未来实施方案。不得将上一轮讨论中的“通过 execute_action”
解释为已批准实现，也不提前给 allowlist 注册占位名称。

## auto 包的联动工作也一起延期

后续若恢复休息能力，需要同时评估 Desktop、SDK 与 auto 包
`arcane-dnd5e-2014-automation`，不能只在 App 新增一个调用原生 shortRest/longRest 的入口。
这里记录的是休息相关依赖，并由 [auto pack TODO](./todo.md) 汇总追踪。
依照唯一技术方案的协作纪律，发现包侧需求只记录背景、需求和改造思路，当前不修改 auto pack。
取消召唤同先攻仍是既定目标，但其包侧改造也等待重构工作统筹，不在本轮直接实施。

已读到的现有实现（源码审查，不代表已安装世界版本或集成验证结果）：

- auto2014-runtime 的 `src/automation.js` 已导出 `restActor`、`restGroup`。
  它们包装原生休息，并叠加 BG3 短休治疗、短休次数消耗及长休重置等逻辑。
- 同文件有 BG3 短休按钮；`dnd5e.restCompleted` hook 还处理既有资源恢复和
  召唤生命周期的长休联动。直接调用原生休息不一定等价于点击 auto 包的休息按钮。
- 部分路径带 `dialog:false` / 自动选择配置，不能未评估就将其当成通用 agent 合同。

恢复此需求时一起处理：

| 区域 | 待确认/修改 |
| --- | --- |
| 休息语义 | 明确采用当前 auto 包规则还是原生规则；agent 与对应 UI 入口结果保持一致，不默默绕开短休次数和治疗逻辑 |
| auto 包 API | 优先复用已有 restActor/restGroup；如需补能力标识、稳定返回值、完成信号或精确目标校验，在 auto 包实现，不在 App 复制规则 |
| 目标范围 | auto 包支持 group 不等于跑团可以发现世界外队伍；校验本次明确目标及当前 Token 范围，避免 group 成员扩出范围 |
| 消耗与 hooks | 明确短休次数/资源恢复的唯一执行责任，核对直接调用与 restCompleted hook 不会漏处理或重复处理；不以此扩展职业动作支持范围 |
| 人工选择 | 明确生命骰等选项如何交给 DM；复用配置前核查是否跳过了必要选择 |
| 回执与失败 | 统一原生休息、auto 后处理、批量成员的完成/取消/部分成功信号；后处理失败不重做整个休息 |
| 版本与发布 | 如 API 改变，auto 包、SDK、Desktop 共同定义兼容版本或 capability；不兼容时写前说明，不能先休息再发现接口缺失 |

联调至少覆盖：同一角色 UI 与 agent 结果对比、短休次数耗尽、长休重置、明确批量目标、
人工取消、auto 后处理失败及重复投递。只读检查既有法术/召唤联动是否保持原行为，
不为休息补新的跨战斗生命周期系统，也不自动修改玩家世界数据。

上述事项是后续评估清单，不预设全部都要改代码；原入口已满足的部分直接复用。
当前不实施 auto 包休息改造，也不把已有 auto API 接入模型工具。

## 重新评估的依据

- 收集实际需求：休息频率、语音使用比例、批量目标数量、用户是否经常因切回界面中断操作。
- 对比原生点击、独立工具、统一执行入口的总交互成本；固定模型测工具定义/token、
  调用次数和攻击/状态设置的 p50/p95 回归，而不只统计接口数量。
- 若决定实施，再定义正式系统休息、生命骰等人工选择、资源回读、取消/部分成功与
  不确定时禁止重复执行的合同；不能用 HP/法术位 patch 冒充完整休息。
- 明确单人/批量、目标范围与战斗中休息策略，不借此恢复世界 Actor/队伍补充发现。
