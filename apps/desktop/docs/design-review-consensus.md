## 1. 双方已对齐：会话存在与删除

**对话文件是会话存在的唯一依据；文件丢失，就视为会话已删除，关联数据不承担恢复职责。**

不区分文件缺失是用户主动删除、意外丢失还是删除中途崩溃造成的；这些情况采用相同的会话清理语义。

任务 journal、renderer 草稿、导航和活动数据中即使仍有部分用户输入或元数据，也不据此重建会话，不为保留这些残留建立恢复机制。

据此确定：

- 删除 SessionDeletions 的四态 WAL，不再为区分主动删除和意外丢失持久化删除意图。
- 正常删除先删除对话文件，再清理关联数据。
- 中途崩溃留下的关联数据，在启动对账时按不存在对应对话文件处理，包括任务记录、导航状态、活动数据和 renderer 草稿。
- 旧通知的目标会话不存在时，按已删除处理。

实现约束：扫描失败不能当成文件不存在。例如目录读取失败时，不据此执行差集删除。该约束不需要额外事务机制。

本项只决定删除和关联数据清理，不据此推导退出时是否等待外部操作；退出策略单独讨论。

## 3. 本轮结论：归档不为提交路径增加执行围栏

**归档负责收纳会话，不干预用户已经发起的工作。发送后发生归档，允许该次发送继续执行。**

低频归档操作若要给高频提交路径增加检查，必须说明具体保护了什么用户利益。仅仅可能出现“归档后任务才开始”，没有证明数据损坏或错误执行，不足以支持这类围栏。

据此确定：

- 不再将“归档会话绝不能开始执行”作为提交路径必须维护的不变量；移除为此设置的归档状态检查，不是将两处检查合并成一处继续保留。
- 归档页不提供发送入口可以作为界面约定保留，不自动扩展为后端多层执行围栏。
- Codex 收回用发送与归档的异步竞争为现有重复检查辩护；此前的时序例子是假设场景，并非已证实的当前代码故障。
- `/compact` 分支的存在也不能单独证明归档围栏必要；必须先证明被保护的规则有实际收益。

通用评审原则：先说明违反某条不变量会造成什么具体损失，再决定是否需要执行检查，不能仅以维护自行规定的不变量为理由增加机制。

范围：本轮决定归档对提交的约束，不据此删除其他用途的检查，也不代表所有内部状态检查都无必要。内部 owner 的检查原则已在第 4 节对齐。运行中归档按钮是否放开另行确认，本项不自动修改该界面行为。

## 4. 双方已对齐：R2 唯一执行者与按需边界校验

**每个必要的不变量只有一个执行者；一个状态机只有一个 owner，其他模块通过公开动词操作。同进程内部层层重复断言全部删除。**

输入校验集中在三个真实边界：IPC 入口、磁盘读写、子进程／上游调用。边界不是机械添加检查的理由：入口实际能收到什么错误或越权请求，就在那里处理；已经由通道、数据结构或调用契约保证的，不重复检查。

- IPC 身份检查用于阻止非授权页面调用内部接口；若通道本身已保证只有授权界面可调用，不再额外重复检查。
- 输入格式检查用于处理跨边界参数错误，给出明确结果；不逐层校验内部生成的对象。
- 路径归属检查用于防止删除任意文件。若接口只接收会话 ID，由主进程可信映射解析出目标路径，且映射已保证归属，内部不再重复验路径。
- 唯一 owner 可以维护有具体收益的执行条件：删除前解除写入能力、停止中的任务不吞掉新输入、同一命令重试不重复执行。这些条件不在其他层镜像维护。
- 非边界上的 `assert*` 或执行检查必须说明防止的具体错误、实际后果及唯一执行者；“防御性编程”“可能有竞态”本身不构成理由。无法说明收益则删除。

后续实现时将信任边界图及不变量归属写入 architecture.md，评审按以上原则核对。当前只记录共识，不表示代码已整改。

以下为核对 `5cef239` 后对原则的具体应用。原提案没有逐一编号“六层”“五道”，这里按具体条件列出，避免用数量代替代码证据。停止失败 UI、强制停止及运行中归档入口等明确留待讨论的行为，不因本原则通过而自动确定。

### 4.1 删除路径

| 检查或机制 | 处置意见 | 理由与归属 |
| --- | --- | --- |
| main 和 Registry 两处 `assertDeletable` | 删除这两处调用及该断言中的归档前置要求 | 删除不需要先归档；归档页可继续作为 UI 删除入口。 |
| `assertDeletable` 因导航存储损坏拒绝删除 | 删除 | 导航不是对话存在的依据，不应阻止删除对话文件。 |
| `assertDeletable` 因任务忙而拒绝进入删除流程 | 删除 | 删除流程已有停止步骤，不必让用户先自行停止再删除。 |
| IPC 调用者、目标身份及磁盘路径归属检查 | 真实边界按需处理，已有保证不重复检查 | 防止越权调用、任意文件删除或操作错误会话；若通道或可信 ID 映射已保证，则不另加同一检查。内部传递已解析目标。 |
| 删除中重复请求共享同一个操作 | 保留在 Registry | 属于幂等处理，不拒绝用户，不重复停止、销毁和创建替代会话。 |
| 删除期间阻止新提交、新加载注册到该会话 | 保留一个生命周期 owner 的准入规则，收拢散落判断 | 仍在运行的写入者可能在 unlink 后重新写出对话文件，违反“删除后会话不存在”。与不删除数据的归档不同。 |
| 删除前等待写入者停止 | 保留停止与收尾这一执行步骤 | 先解除写入能力，再删除文件；不要求用户额外操作。停止失败的 UI 和强制停止方案另议。 |
| `abort()` 返回后重复判断 `stopped.ok` 和 `target.busy` | 收进停止接口的成功/失败契约，删除调用层重复状态推断 | 当前 TaskCoordinator.stop 会等待 abort 和 run；停止 owner 应报告结果，Registry 不旁路读状态再次裁决。不能只删判断而忽略接口失败结果。 |
| SessionDeletions WAL、持久删除身份检查 | 删除 | 按第 1 节采用文件存在性与启动对账。运行中准入状态不承担持久化删除事实。 |
| Registry.select 在 await 前后及返回前散落的删除状态检查 | 收拢到生命周期 owner 的加载/删除协调 | 不原样保留层层检查；异步加载完成后不能把已经删除的 host 再注册回来。该结果约束需要保留。 |

### 4.2 提交路径

| 检查或机制 | 处置意见 | 理由与归属 |
| --- | --- | --- |
| main、submitInput、compact 中的 `assertWritable` | 删除归档/导航健康状态围栏 | 导航损坏不妨碍对话执行，归档竞争不构成执行损失。此次还核实到 compact 有第三处调用。 |
| 空输入、图片结构及请求目标检查 | 集中在 IPC 边界按需处理 | 拒绝无内容请求、解析输入、避免发到错误会话；已有契约保证的内容不重复校验。 |
| 工作目录有效性 | 磁盘边界保留一次 | 不在用户指定项目缺失时改用其他目录执行。 |
| 模型凭据可用性 | SDK 调用适配入口保留一次并转换为用户可行动错误 | 缺少凭据无法调用模型，不属于归档或内部信任围栏。 |
| AgentHost.closing / deleting | 收拢为生命周期 owner 的一次执行准入，不在多层镜像检查 | 已销毁或即将销毁的执行环境不能再接受工作；不原样保留每个模块各自维护标志的做法。 |
| submitInput 的 session 未初始化断言 | 内部删除，初始化由调用契约保证，SDK 边界处理实际不可用错误 | 正常 IPC 已先 ensureStarted，不为内部调用者重复设防。 |
| TaskCoordinator.submit 的 stopping 检查 | 保留在 TaskCoordinator | 当前 busy 包含 stopping；删此检查会把新输入作为旧任务补充接受，drain 随后退出并把它标为 cancelled。真实后果是已返回 accepted 的新消息不执行，不是单纯状态不整齐。改为自动创建下一任务属于另一个行为变更，不在本次清理中引入。 |
| commandId 重复及内容冲突检查 | 保留在 TaskCoordinator，唯一执行 | 同一次发送重试不应执行两遍；同 ID 不同内容不能返回旧输入的成功回执。 |
| AgentHost 审批旁路驱动 TaskCoordinator 状态 | 删除旁路实现，统一走 TaskCoordinator 公开动词 | 接受原 R2 的唯一状态 owner 要求。 |

本轮核对同时纠正此前的归档竞态例子：chat:prompt 中的 prepare 是同步调用；不能把假设的“等待附件几秒”作为当前双份断言必要性的证据。

R2 共识限定保留：按实际风险设置的边界校验，以及唯一 owner 对生命周期、任务停止、命令去重的必要执行条件。其余同进程重复断言删除。

## 5. 双方已对齐：快照缓存 ROI 不明确则不保留

**看不清 ROI 就不做。已经实现、删除比新增困难，都不是保留功能的理由。**

本项针对 renderer 的跨会话快照缓存（snapshotCache）。实际切换仍请求主进程最新快照，缓存用于先展示旧快照。已有性能记录没有无缓存对照，不能证明这层优化的必要性；规格和测试要求缓存命中，也不构成用户收益证据。

## 6. 双方已对齐：移除任务 journal，按跨重启用途保存最小状态

**不保留当前任务 journal。持久化只服务于明确需要跨重启保留的用户内容和选择，不为已经终止的执行过程保存整套状态流转。**

### 6.1 保存内容与重启行为

| 内容 | 共识 |
| --- | --- |
| commandId / fingerprint 去重 | 放在 TaskCoordinator 内存 Map，随 host 生命周期结束；保留同一运行期重试去重，放弃跨重启旧命令身份重试和幂等保证。 |
| 已接受但未消费的输入 | 每会话一个 pending-input.json，存未消费输入列表及必要附件数据，整体重写；接受时保存，消费后移除，无追加日志、checkpoint 或 compaction。不能以单条槽位覆盖连续补充输入。 |
| 重启后的未处理输入 | 启动对账后展示为已中断、可由用户重发；不自动执行。 |
| renderer 旧 outbox | 恢复为待用户检查的草稿或待重发内容；用户重发生成新 commandId，不沿用旧身份直接重试。与未消费输入按身份合并展示，避免同一输入重复出现，不覆盖用户另存的草稿。 |
| 模型选择 | 存入持久会话元数据，同时覆盖 pending_model 和缺凭据时的 _currentModelRef；保存后移除 canEvict 为这类内存选择设置的保留条件。 |
| 任务／输入中间状态、提问卡状态 | 放弃逐事件持久化，不恢复旧提问卡或旧 resolver，不支持跨重启补交旧提问回答。已进入对话文件的回答随历史保留。 |
| 任务中断摘要 | 沿用现有 ActivityCenter 启动时的中断转换；不从 pending-input 是否为空推导整个任务是否中断，也不据此重建提问卡。 |

### 6.2 清理与实施要求

- 删除任务 journal 的 replay、checkpoint 版本处理、compaction 阈值和坏记录阻塞会话的路径；旧数据迁移只保留上述目标状态，不保留旧日志系统作为长期兼容机制。
- 同步修改 renderer 持久 outbox 和后端 acceptedCommandIds 的配合方式，不能只删 journal replay 而保留跨重启旧命令重试按钮。
- 新状态文件使用整体替换的可靠写入方式；损坏时隔离、允许继续使用并告知，不恢复“坏一条就永久阻塞会话”的策略。
- 对话文件不存在时，按第 1 节清理 pending-input 和模型元数据等关联数据；仍有必要的关联清理，但无需任务日志事务协调。
- 不自动续跑任务，不承诺恢复已经中断的外部执行。若将来有明确新需求，再按实际消费者评估持久化方案，不预留日志基础设施。

当前仅记录原则与整改要求，尚未修改产品代码。

## 7. 双方已对齐：完全移除 Foundry 操作锁

**Foundry 操作锁完全不要。当前看不到加锁的明确价值，采用无锁方案，不替换为读写锁或局部互斥。**

当前打开页面、截图、页面脚本和结构化 runtime 调用均经过同一个资源键，导致读取也互相阻塞。本结论取代此前“至少改为读写锁、逐项评估互斥”的意见，不再以锁粒度优化作为整改目标。
