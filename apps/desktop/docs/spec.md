# Desktop 多会话连续工作体验 Spec

状态：终态体验契约，实施中；不代表全部已实现或验收通过。当前证据与缺口见 [验收审计](acceptance-audit.md)。

日期：2026-09-07

适用范围：ArcaneDesk Desktop 的备团、战斗模式及其会话

模块职责、接口与关键时序见 [架构设计](architecture.md)。本文件定义体验契约，架构设计说明如何承接这些要求。

## 1. 终态是什么

用户交代 A 去做一件事，转身与 B 讨论另一件事，再回到 A，应该像回到一位仍在工作的同事身边：看得见他做到哪里，知道是否需要自己参与，已有成果完整保留。

**切换会话只改变当前查看对象。任务的执行不依赖用户是否正在看它。**

用户随时能回答三个问题：

- 哪些任务还在进行？
- 哪些任务需要我处理？
- 我离开以后，这个会话有什么新进展？

本设计统一同模式切会话与跨模式切换的体验。模式决定会话的工具、工作环境与能力，不改变后台运行语义。

## 2. 一段完整的目标体验

1. 用户在备团会话 A 提交“整理今晚的冒险素材”。消息立即显示，A 标记为“运行中”。
2. A 开始读取资料，当前过程显示“正在读取资料”。用户新建备团会话 B，询问另一段剧情。B 立即打开，A 在侧栏继续显示运行状态。
3. 用户切到战斗模式查看 C。跨模式的活动入口仍显示 A、B 的运行情况；某个任务需要处理时不会被藏在另一个模式中。
4. A 遇到需要用户决定的问题，状态变成“需要你处理”。出现一次不抢焦点的提示：“整理今晚的冒险素材：需要你选择素材范围”。点击可回到 A 的问题位置。
5. 用户回到 A，看到离开后的新增内容、问题及已有结果；输入回答后 A 继续推进。用户再回 B，B 的草稿、滚动位置和展开的过程仍在。
6. A 完成，在侧栏标记“已完成 · 未读”，不自动切走当前会话。用户点开后看到完成结果及“上次看到这里”的分界。
7. 用户看过最新结果，未读标记消失；完成状态保留，直到开始下一轮任务。

如果 A 始终无需用户参与，它应从后台运行直接走到完成，用户不用切回“维持”它。

## 3. 核心对象与语义

| 对象 | 定义 | 约束 |
| --- | --- | --- |
| 会话 | 一段长期保留的对话及其工作上下文 | 有稳定身份，模型、工作目录、草稿、历史与阅读位置互相隔离 |
| 任务 | 用户一次发起、直到完成、失败或停止的工作 | 同一会话最多一个未结束任务；执行中可以接收补充要求 |
| 当前会话 | 用户正在查看和输入的会话 | 只是视图选择，不拥有其他任务的生杀权 |
| 模式 | 备团或战斗的能力与界面上下文 | 会话创建后归属固定；切模式不停止任何任务 |
| 未读进展 | 用户尚未看过的新输出或状态变化 | 独立于任务运行状态，不按流式片段累计数量 |

补充要求属于当前未结束任务。若任务已结束，新的输入开始下一任务。提交归属由执行侧在接收时确定，并回传给界面，不能由界面上可能滞后的“运行中”标记决定。

## 4. 界面结构

### 4.1 会话导航

- 宽窗口保留常驻会话侧栏；窄窗口允许收起为入口，始终显示运行中数量及需要处理的数量。
- 当前模式显示自己的会话列表；跨模式“活动”区域汇总运行中、排队中和需要处理的会话，点击后自动进入所属模式和会话。
- 每个列表项包含标题、任务状态、未读标记。当前选中态、任务状态和未读态分别表达，不能只靠同一个圆点或颜色。
- 普通文字输出不反复重排会话列表。新建会话和用户主动选择可以改变最近访问顺序；状态变化只更新原位置。
- 后台完成的任务可在活动区域保留至用户查看或主动清除，随后仍可从所属模式的会话列表找到。
- 不要求用户展开会话抽屉才能知道有任务在后台工作。

### 4.2 对话区

- 顶部显示会话标题及真实任务状态；运行时提供“停止”入口。
- 当前工作过程显示实际阶段、当前工具及持续时间。详情可展开，默认不让高频工具输出淹没结果。
- 进行中的过程不能被画成已完成，也不能因切换恢复而重新从零计时。
- 半截回复、思考内容按现有展示策略保留；切回后继续更新同一条内容。
- 失败、停止、等待用户与成功完成有明确区别，不能统一显示“已就绪”。
- 不展示虚构百分比。未知总量时显示具体动作或“等待响应”。

### 4.3 输入区

- 每个会话独立保存草稿及待发送附件，切换后完整恢复。
- 空闲时输入表示新任务；执行中输入表示补充当前任务，发送入口清楚标注该语义。
- 补充消息先显示“正在发送”，执行侧确认接收后显示“已接收，等待处理”；只有确实进入模型处理上下文后，才显示“已交给助手处理”。
- “已交给助手处理”不等于要求已经完成。后续是否落实通过实际结果表达。
- 发送失败保留原文、附件与重试入口。用户主动重试时不能产生重复提交。
- 停止过程中保留草稿，暂不向将结束的任务注入新要求；停止完成后允许发起下一任务。

## 5. 任务状态

任务状态由执行侧维护。前端的选中、隐藏、重建与刷新都不能自行改变任务状态。

| 状态 | 用户看到什么 | 如何离开该状态 |
| --- | --- | --- |
| 空闲 | 可以开始新任务 | 用户提交任务 |
| 排队中 | 等待执行，可见排队原因，可取消 | 获得执行额度后运行，或用户取消 |
| 运行中 | 当前阶段、工具或等待响应，以及持续时间 | 需要用户、等待资源、结束或收到停止请求 |
| 等待资源 | 等待哪类资源，以及哪个任务正在使用它 | 资源可用后继续，或用户停止 |
| 需要你处理 | 具体问题或现有权限机制要求的操作 | 用户回应后继续，或用户停止 |
| 正在停止 | 已请求停止，正在等待执行退出 | 执行侧确认停止，或工作在停止生效前已完成 |
| 已完成 | 完成结果及产物入口 | 用户提交下一任务 |
| 失败 | 失败原因、已有成果、可行的下一步 | 用户重试或提交新任务 |
| 已停止 | 停止原因及已保留的进展 | 用户明确要求继续或提交新任务 |

补充规则：

- 工具的一次失败不必立即令整个任务失败；助手仍在恢复或尝试其他方法时保持运行中，并展示真实过程。
- 自动重试是运行中的一个阶段，显示“正在重试”；只有后端确有重试行为时才展示。
- 长时间没有新文字不等于停止。工具还在执行时显示工具及持续时间；无法确认执行状态时显示同步异常。
- “正在同步”“状态暂不可用”属于界面同步状态，不得覆盖或伪造任务终态。同步异常时显示最后更新时间，恢复后校准。
- 未开始的排队任务取消后显示“已取消”，不伪称已执行或完成。
- 停止请求与正常完成竞态时，以执行侧确认的结果为准。

## 6. 切换与返回的行为契约

### 6.1 离开会话

- 新建会话、打开历史会话、切换模式、收起侧栏、最小化窗口，都不隐式停止任务。
- 切换不等待原任务结束，不向原任务自动发送任何消息，也不重复提交原任务。
- 快速连续选择 A、B、C 后，最终展示最后一次选择的 C。迟到的加载响应不能把用户带回 A 或 B。
- A 的迟到输出、错误或发送结果，只能更新 A，不能改变 B 的正文、草稿、模型或停止按钮。

### 6.2 返回会话

- 优先展示已有现场；需要补齐数据时显示轻量同步状态，不能先清空成欢迎页。
- 恢复已完成历史、当前半截内容、正在运行的工具、待处理问题和真实任务状态。
- 用户离开时处于底部：返回后跟随最新进展。
- 用户离开时在翻历史：返回原阅读锚点，显示“有新进展”入口，不强制滚到底部。
- 阅读锚点应关联消息，不能只依赖容易因内容高度变化失效的像素位置。
- 只有当前会话可见且用户实际到达新增内容时，才推进已读位置。仅切换到该会话不清掉屏幕外的未读结果。
- 后台已完成时，返回直接展示终态；不能先显示仍在运行，再等待一个已经错过的结束事件。

## 7. 后台反馈与打扰程度

| 事件 | 当前会话可见 | 用户正在其他会话 | 应用不在前台 |
| --- | --- | --- | --- |
| 普通进度 | 更新正文和过程 | 更新列表状态，不弹提示 | 不通知 |
| 完成 | 显示结果 | 未读标记及一次轻提示，不抢焦点 | 用户已启用系统通知时通知一次 |
| 需要用户处理 | 展示待处理项 | 明显标记及一次可直达的提示 | 用户已启用系统通知时通知一次 |
| 失败 | 展示原因和后续入口 | 失败标记及一次轻提示 | 用户已启用系统通知时通知一次 |

- 同一状态变化只提示一次；恢复页面、补拉历史、重复事件都不能再次提醒。
- 短时间多个完成事件可以合并提示。正在输入时，不用遮挡输入区的浮层打断用户。
- 提示默认使用会话标题与状态，不把正文、文件内容放进系统通知。
- 需要处理的状态持续保留到问题被解决。该机制只呈现真实交互需求，不新增无必要的审批流程。

## 8. 停止、删除和应用生命周期

### 8.1 停止

- 停止始终针对明确会话的明确任务。即使点击后马上切到 B，也只能停止 A。
- 点击后立即显示“正在停止”，执行侧确认之前不显示“已停止”。
- 停止较慢时说明正在等待哪个操作退出，不假装已经结束。
- 已完成的外部操作不会因停止而自动撤销；已有输出和可确认的成果保留。
- 停止后可以点击“继续处理”或输入新要求。继续是带上下文的新执行，不承诺从某条机器指令精确续跑。
- 自动重试、排队与等待资源中的任务也必须可停止；停止后不应再悄悄启动。

### 8.2 删除

- 删除空闲或已结束会话沿用现有删除确认规则。
- 删除未结束会话时，明确提供“停止并删除”操作；等待停止确认后才删除。
- 删除失败或停止未完成时保留记录与状态，不能从列表消失但仍在后台执行。

### 8.3 最小化、关闭与重启

- 最小化或隐藏窗口，只要应用执行进程仍存活，任务继续执行。
- 关闭最后一个窗口但有未结束任务时，明确提供“后台继续”“停止任务并退出”“取消”。仅在确实具备后台进程及重新打开入口时提供“后台继续”。
- 明确退出应用时，有未结束任务则说明影响，由用户选择停止并退出或取消；正常退出等待停止结果，不能无限卡住而没有反馈。
- 系统强制结束、崩溃、重启不承诺保持执行。下次打开时恢复历史，将未确认结束的任务标为“执行中断”，展示恢复入口。
- 不自动重放可能产生外部副作用的操作；恢复先核对已有成果，再继续工作。
- 前端刷新或重建、执行进程仍存活时，重新同步运行现场，不创建新任务、不消耗一次新的模型请求。

## 9. 并发与上下文隔离

- 不同会话可以同时推进；每个会话各自持有模型、工作目录、任务状态、输入队列和运行现场。
- 修改 B 的模型或工作目录不能影响 A 正在执行的上下文。更换工作目录通过新建会话完成。
- 设置默认模型只影响新会话。当前任务执行中的模型更改默认用于下一任务，界面注明生效范围。
- 多任务共同操作 Foundry 页面、世界状态或同一文件时，需要协调冲突操作。能安全并行的操作继续并行。
- 对无法判断是否冲突的受控写操作采用保守串行策略；不能只依赖助手自行记住“不要冲突”。不承诺阻止外部程序自行修改资源。
- 用户看到“等待会话 A 完成 Foundry 操作”，资源释放后自动继续。排队应避免任务长期饥饿；取消任务会撤销其尚未开始的资源请求。
- 达到运行额度时，新任务明确进入排队，不静默停止旧任务。运行额度是独立配置，不因用户切换视图而变化。
- 内存回收可以释放已结束会话的运行实例，但不能回收运行中、待处理或待停止的任务；重新打开仍能恢复历史与阅读状态。

## 10. 系统必须满足的行为不变量

本节定义实现必须保证的结果，不限定组件拆分或具体 SDK 用法。

1. 执行归会话和任务所有，视图只负责查看与输入。
2. 每次命令、每条事件都能定位所属会话与任务，迟到事件不能污染新任务。
3. 运行状态只有执行侧一个权威来源；前端即时反馈与已确认状态有明确区别。
4. 后台事件即使不渲染正文，也必须更新该会话的可恢复状态及列表摘要。
5. 任意时刻的恢复数据足以重建当前现场，不能只包含完成的历史消息。
6. 快照与后续事件之间有顺序及去重约定；切换期间不能漏内容、重复消息或以旧状态覆盖新状态。
7. 会话导航不触发停止、释放运行实例或重新提交任务。
8. 未收到完成结果的工具不能显示成功；未确认停止的任务不能显示已停止。
9. 已读位置与通知去重信息可以恢复，页面重建不引发重复提醒。
10. 诊断信息可关联会话、任务、事件顺序及状态变化，用于区分执行停滞和界面同步停滞；不为此额外记录敏感正文。

## 11. 体验验收

以下为目标验收门槛，不是当前版本的实测表现。

### 11.1 必须通过的场景

| 场景 | 验收结果 |
| --- | --- |
| A 流式生成时打开同模式 B，再回 A | A 未中止，半截回复保留，后续内容接在同一条消息上 |
| A 执行长工具时切换模式，再回 A | 工具仍显示实际运行状态及原起始时间，没有虚假完成 |
| A 在后台完成后再打开 | 直接看到完整结果和完成状态，不依赖新事件唤醒 |
| A 在后台失败或需要处理 | 无需打开 A 就能发现；点击提示可定位到具体内容 |
| 快速 A→B→A，且响应乱序到达 | 最后选择生效，正文、模型、草稿和状态均不串会话 |
| 快照返回前后恰好发生任务结束 | 最终显示终态，消息不丢失、不重复，状态不倒退 |
| 在 A 发送或停止后立刻进入 B | 后续回执只影响 A，B 可以独立操作 |
| A、B 各有草稿、附件和历史阅读位置 | 来回切换后分别完整保留 |
| 当前会话在翻历史时收到新输出 | 不抢滚动位置；新进展入口可跳到最新 |
| 执行中提交补充要求，恰逢任务结束 | 每条输入得到明确归属与接收状态，既不丢失也不重复执行 |
| 前端刷新，执行进程未退出 | 任务继续，现场恢复，不发起新的模型调用 |
| 执行进程异常结束后重启 | 显示执行中断及已有成果，不假装仍在运行，不自动重复外部操作 |
| 两会话争用同一受控资源 | 冲突操作排队，原因可见；一方取消不影响另一方 |
| 超过运行额度后取消排队任务 | 任务从队列移除，以后不会意外开始 |
| 删除正在执行的会话 | 明确停止并删除；停止未确认前会话仍可追踪 |
| 已通知任务被重开或事件被重复投递 | 不产生重复通知 |

### 11.2 响应性目标

- 在约定基准设备、已有会话缓存的条件下，点击切换后 100 ms 内出现选中反馈，300 ms 内展示缓存现场，均以 P95 衡量。
- 本地运行现场正常可用时，切回后 1 秒内完成状态校准；超过 1 秒显示同步提示，不能无反馈空白。
- 正常运行时，执行侧确认状态变化至前端呈现的延迟 P95 不超过 500 ms；按接收到执行事件计时，不包含模型或工具本身的等待。
- 性能验收同时覆盖长历史和配置允许的最大并发任务数；发布前固定基准设备、数据量和测量方法。
- 没有正确性上的“最终会刷新就算通过”：任务归属、停止范围、消息完整性与状态准确性必须始终成立。

## 12. 范围与后续决策

本终态包含同模式多会话并存、跨模式连续工作、现场恢复、后台可见性、通知、输入隔离、停止及退出行为。

不包含跨设备接力、应用进程退出后继续云端执行、任意工具的事务回滚，也不要求提供精确进度百分比。

进入实现设计前还需确定：默认并发额度、后台驻留的操作系统实现、资源协调的具体边界和性能基准。这些参数可以调整，但不得改变“切换不停止任务”和“状态可恢复且可信”的契约。

历史问题与源码调查见 [会话模型隔离与切换问题记录](model-and-session-isolation-spec.md)。其中的分期修复建议是历史背景，本文件以最终用户体验为验收依据。
