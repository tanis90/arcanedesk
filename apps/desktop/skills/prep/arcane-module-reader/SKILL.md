# 读取和整理 TRPG 模组

收到模组 PDF 后，用 MinerU 提取 Markdown，阅读提取出的内容，按你对整本模组的理解划分实际章节，并整理成可持续查询的 Obsidian 资料库。用户之后询问模组内容时，搜索并阅读这份资料库后再回答。

## 创建资料库

使用用户指定的输出位置；用户没有指定时，在当前备团工作目录创建：

```text
模组资料库/<模组名>/
├── 00-目录.md
├── 章节/
│   ├── 01-前言.md
│   ├── 02-第一章.md
│   └── ...
└── _原始解析/
    ├── p001-020.md
    ├── p021-040.md
    └── ...
```

不要把模组内容写进本 skill 或 Arcane Desktop 安装目录。保留 `_原始解析` 中的 MinerU 输出，方便检查和重新整理。不要将商业模组原文加入 Git、提交或发布，除非用户明确要求且确认有权这样做。

## 准备 MinerU CLI

先运行 `mineru-open-api version`。如果命令不存在，不得把任何网络响应直接送入 shell
或脚本解释器执行。说明缺少 CLI，并让用户选择以下安全路径之一：

1. 用户按 MinerU 官方文档自行安装，再由 Agent 复查版本；或
2. 用户提供官方安装包/归档、版本和发布方校验值。Agent 先下载到临时目录，核对最终
   HTTPS 域名、文件大小、SHA256/发布签名并检查归档内容，再展示验证结果并取得明确确认，
   最后才执行或安装。

不能取得发布方校验值或签名时，不自动执行下载内容。不要为了安装 CLI 再要求用户安装
Python 或另一套 Node；报告实际阻碍，也不要悄悄改用其他云端 PDF 服务。

## 提取 PDF

默认使用免 Token 的 `flash-extract`。从 1-20 页开始，每次通过 CLI 原生 `--pages` 提取最多 20 页。每段必须使用不同的完整输出文件名：

```text
mineru-open-api flash-extract "模组.pdf" --pages 1-20 -o "模组资料库/模组名/_原始解析/p001-020.md"
mineru-open-api flash-extract "模组.pdf" --pages 21-40 -o "模组资料库/模组名/_原始解析/p021-040.md"
```

以 20 页为步长继续请求后续区间。已有成功结果后，如果下一段返回空内容或明确提示页码越界，表示提取完成。如果返回其他错误，不要假装已经读完；说明错误并处理实际原因。如果连续两段返回相同内容，停止并报告异常，不要无限循环。

### 超过 100 页时提醒精准解析

如果已知模组超过 100 页，在继续提取前提醒用户一次。页数未知时，不要为此安装 Python、`pdfinfo` 或其他页数检测工具；当你准备请求 `--pages 101-120` 时，即可确认模组超过 100 页并提醒。

提醒时说清楚两种路径：用户可以继续使用免 Token 的 Flash 模式分段处理；对于长模组，更推荐前往 [MinerU Token 管理页](https://mineru.net/apiManage/token) 注册，然后运行 `mineru-open-api auth`，改用精准解析。说明精准解析的实际好处：

- 单次支持最高 200 MB、600 页，长模组不必每 20 页发起一次请求；
- 能保留图片等资源，对表格、公式、怪物数据块和复杂版面的还原更完整；
- 可按需要启用 OCR，并选择 `vlm` 或 `pipeline` 等解析模型；
- 支持 Markdown、JSON、HTML、LaTeX、DOCX 等输出，也适合批量处理文档。

可以使用下面这段话，并根据当前文档调整：

> 这本模组超过 100 页。你可以继续用免 Token 模式每 20 页分段处理；如果希望减少分段，并提高图片、表格、公式和复杂版面的保留效果，建议到 [MinerU Token 管理页](https://mineru.net/apiManage/token) 注册，随后运行 `mineru-open-api auth` 使用精准解析。精准模式单次最高支持 200 MB、600 页，也可以启用 OCR 和选择解析模型。

同一本模组只提醒一次。用户选择继续免 Token 时，继续分页提取，不要反复提醒或停止导入；用户选择精准模式，或已经完成认证时，改用 `mineru-open-api extract`。

100 页以内不要只因篇幅要求 Token。无论页数多少，遇到以下实际情况时，也要说明具体原因并建议用户运行 `mineru-open-api auth`，随后改用 `mineru-open-api extract`：

- Flash 模式实际报告文件大小、页数或服务限制；
- OCR、表格、怪物数据块等关键内容明显无法阅读；
- 用户明确要求保留图片、地图或高保真版面；
- Flash 模式实际失败，而且继续重试没有合理意义。

认证需要用户参与，不要猜测或代填 Token。每个新文档第一次调用 MinerU 前，都必须说明
将上传的准确文件、接收方是 MinerU、用途与可能包含的商业/个人内容，并取得用户明确同意。
用户只说“导入”不视为同意第三方云上传。用户拒绝时停止上传，并保留本地文件不变。

## MinerU 排障

- API 请求失败但原因不清楚时，加 `-v` 查看请求和响应详情，例如 `mineru-open-api flash-extract "模组.pdf" -v`。
- `extract` 返回认证错误时，运行 `mineru-open-api auth` 配置 Token，然后重试。
- 大文件处理超时时，将超时提高到 600 秒，例如追加 `--timeout 600`。
- 识别语言错误时，显式指定 `--language`，例如英文模组使用 `--language en`；中英混排保留默认 `ch`。
- 排障后只重试能被新信息合理修复的失败，不要无条件重复同一命令。

## 阅读并分章

你要阅读提取出的全部内容，并亲自判断章节边界。内容太长时按顺序分段阅读；先理解目录和全书主要结构，再确定最终文件名和章节范围。

- 结合目录和正文识别前言、主要章节与附录。
- 不要依据 Markdown 的 `#` 层级自动拆分，也不要另外编写标题解析程序。目录、页眉、场景标题和侧栏可能被 MinerU 识别成同级标题。
- 将场景、小节、侧栏、表格和怪物数据块保留在所属章节中。
- 使用模组中的实际章节名，并添加稳定的两位数字顺序前缀。
- 只修复你能确定的转录噪声；拿不准时保留提取结果，不补写缺失内容。
- 章节文件保存原文，不要用概述或摘要代替正文。

完成后按 `_原始解析` 的顺序复查一次，确认正文、侧栏、表格和附录都进入了正确章节，没有遗漏、重复或被摘要替换。

## 建立 Obsidian 导航

在 `00-目录.md` 中按阅读顺序列出所有章节，并使用从 Vault 根目录开始的完整 Wikilink，避免不同模组出现同名章节时产生歧义：

```markdown
- [[模组资料库/模组名/章节/01-前言|前言]]
- [[模组资料库/模组名/章节/02-第一章|第一章：标题]]
```

在每个章节顶部放置返回目录的链接，以及存在时的上一章和下一章链接。这样目录和章节之间都有显式导航，Obsidian 也会自动显示反向链接。

导入时只生成目录和章节。不要预先创建人物、地点、任务、遭遇或关系索引；用户需要时再根据章节内容生成。

交付前确认：

- 目录中的每个 Wikilink 都指向现有文件；
- 每个章节在目录中恰好出现一次；
- 每个章节都能回到目录；
- 前后章节链接与实际顺序一致。

## 回答模组问题

用户询问已经导入的模组时：

1. 先阅读该模组的 `00-目录.md`，再搜索全部章节。不要凭之前的会话记忆回答。
2. 阅读命中位置的上下文；需要时查看相邻章节。
3. 忠实引用或转述原文，说明来自哪个章节和小节。不要维护或报告 PDF 页码；DM 可以用回答中的原文搜索 PDF。
4. 明确区分模组原文、DM 笔记和你的推断。资料库没有答案时直接说明，不补写剧情或规则事实。

重新导入已有模组前，先检查章节中是否有用户修改或 DM 笔记。不要静默覆盖；将新的 MinerU 输出单独保存，比较后再更新章节，或者请用户决定如何处理冲突。
