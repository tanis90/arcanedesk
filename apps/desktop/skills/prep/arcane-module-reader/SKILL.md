# 读取和整理 TRPG 模组

收到模组 PDF 后，用 MinerU 提取 Markdown，阅读提取出的内容，按你对整本模组的理解划分实际章节，并整理成可持续查询的 Obsidian 资料库。用户之后询问模组内容时，搜索并阅读这份资料库后再回答。

## 用户交互预算

交互预算恒定 1 次：规则只有一条——你的上下文里已经有用户回答过「那一次提问」的记录，
就不再问，直接干；没有这条记录，第一次上传前问那一次。问过之后，后续所有模组 PDF 的
提取、分章、建导航、冲突备份等全部过程不再有提问、确认或选择——用户见过一次就知道
是怎么回事，他不同意自然不会再把新 PDF 交给你，反复问是打扰。重新导入已导入过的模组
也一样不问，冲突按「重新导入」节的默认规则处理。新增任何用户交互前，先论证为什么不
能归入这一次提问。

## 创建资料库

使用用户指定的输出位置；用户没有指定时，用当前备团工作目录（agent 会话的 cwd）下的
`模组资料库/<模组名>/`，一律解析为绝对路径，写进那一次提问和最终报告：

```text
模组资料库/<模组名>/
├── 00-目录.md
├── 章节/
│   ├── 01-前言.md
│   ├── 02-第一章.md
│   └── ...
└── _原始解析/
    ├── p001-020.md
    ├── p021-040.md
    └── ...
```

不要把模组内容写进本 skill 或 Arcane Desktop 安装目录。保留 `_原始解析` 中的 MinerU 输出，方便检查和重新整理。不要将商业模组原文加入 Git、提交或发布，除非用户明确要求且确认有权这样做。

## 准备 MinerU CLI（自治，不问用户）

先运行 `mineru-open-api version`。命令可用时直接跳到「那一次提问」。

命令不存在时，用 MinerU 官方安装脚本安装（零依赖单二进制，不需要 Python 或 Node），
只从这两个官方 URL 获取。安装是工具准备（技术细节）：agent 做机器校验并事后报告，
不向用户展示脚本内容或哈希串求确认。

- macOS / Linux：`https://cdn-mineru.openxlab.org.cn/open-api-cli/install.sh`
- Windows PowerShell：`https://cdn-mineru.openxlab.org.cn/open-api-cli/install.ps1`

不得把任何网络响应直接送入 shell 或脚本解释器执行。正确做法是先下载到临时目录：

```bash
# macOS / Linux
curl -fsSL -o /tmp/mineru-install.sh "https://cdn-mineru.openxlab.org.cn/open-api-cli/install.sh"
```

```powershell
# Windows PowerShell
Invoke-WebRequest -Uri "https://cdn-mineru.openxlab.org.cn/open-api-cli/install.ps1" -OutFile "$env:TEMP\mineru-install.ps1"
```

执行前核对最终 HTTPS 域名是 `cdn-mineru.openxlab.org.cn`，并亲自读一遍下载到的脚本
（它是纯文本），确认其行为只是下载二进制、加入 PATH；执行后无条件计算脚本与二进制的
SHA256——CDN 不提供发布方校验值，计算值作为本次安装指纹写进报告，不宣称与任何官方
哈希匹配。脚本会把二进制装到 `$HOME/.mineru/bin` 并把该目录加进用户 PATH，在报告里用
一句大白话说明这件事。安装完成后用绝对路径运行 `mineru-open-api version` 复查版本。
Windows 上始终用二进制的绝对路径调用；在 Git Bash 等类 Unix 终端里直接执行 exe 可能
报 Permission denied，应经 PowerShell 调用，例如
`powershell.exe -NoProfile -Command '& "C:\Users\<用户>\.mineru\bin\mineru-open-api.exe" version'`。

不要使用第三方镜像或这两个官方 URL 之外的来源。不要为了安装 CLI 再要求用户安装 Python
或另一套 Node；安装失败时报告实际命令输出和剩余阻碍，不要悄悄改用其他云端 PDF 服务。

## 那一次提问

CLI 就绪后、任何模组内容上传之前，先检查自己的上下文：已经有用户回答过这次提问的
记录，跳过本节直接提取。没有记录时，先跑 `mineru-open-api auth --show`（纯本地查询，
不上传任何内容），然后按探测结果发起唯一的一次提问：

- **已配置 Token**（提问形态 A，上传确认）：「《模组名》要上传到 MinerU 的服务器解析，
  接收方是 MinerU，内容可能包含商业/个人信息。你已配置 Token，会用精准模式整本解析。
  可以开始吗？」
- **未配置 Token**（提问形态 B，披露 + 选择合并成一句）：「《模组名》要上传到 MinerU
  的服务器解析，接收方是 MinerU，内容可能包含商业/个人信息。MinerU 有个免费精准模式：
  图片、表格、怪物数据块还原更好，整本一次解析不用分段，但需要先到 mineru.net 注册一个
  免费 Token。要我带几步注册，还是直接用免 Token 模式开始（图片和表格会变成占位符，
  每 20 页分一段）？」

用户答一句即放行，之后的文档沿用这次回答，不再重问。未取得用户明确同意前不得上传；
用户只说“导入”不视为同意第三方云上传。用户拒绝上传时停止，保留本地文件不变。

用户选择注册 Token 时，给精确点击步骤（浏览器打开
<https://mineru.net/apiManage/token> → 注册/登录 → 创建并复制 Token）。注册引导是那
一次提问的延续，不算新的交互点。用户把 Token 发给你后，帮他存进本机配置并验证生效，
不要只停留在本次任务临时使用——否则用户下次开新对话又得注册一遍：

1. 若 `~/.mineru/config.yaml` 已存在，先复制为带时间戳的备份：`auth` 会直接覆盖旧
   Token，不留副本。
2. 用 stdin 管道写入，避免 Token 出现在命令行参数和进程列表里：
   `printf '<Token>\n' | mineru-open-api auth`。
3. 跑 `mineru-open-api auth --show` 回读验证（纯本地查询），确认显示
   `Token source: config`，且掩码的首尾几位与用户给的 Token 一致。
4. 之后直接运行 `extract`，CLI 会自动读取配置，无需再设 `MINERU_TOKEN` 环境变量。

验证通过后明确告诉用户：Token 已保存在本机，下次新对话直接用，不用再注册。Token 本
身不回显、不写进报告、不提交进 Git；报告里最多写掩码首尾用于辨认。

## 提取 PDF

**精准模式**（已配置或新注册 Token）：`mineru-open-api extract "模组.pdf" -o "<资料库>/_原始解析/"` 整本一次解析（单次上限 600 页 / 200 MB）。运行中返回 HTTP 401 或 `msgCode A0211` 表示 Token 失效：不打断流程，改用下方免 Token 分段继续跑完，在报告里说明 Token 已失效并附重新配置的建议。

**免 Token 模式**：用 `flash-extract --pages` 分段，每段最多 20 页（单文件另有 10 MB
上限；某段因体积超限失败属实际限制，缩小该段页距重试即可）。从 1-20 页开始，每段必须
使用不同的完整输出文件名：

```text
mineru-open-api flash-extract "模组.pdf" --pages 1-20 -o "模组资料库/模组名/_原始解析/p001-020.md"
mineru-open-api flash-extract "模组.pdf" --pages 21-40 -o "模组资料库/模组名/_原始解析/p021-040.md"
```

以 20 页为步长继续请求后续区间。已有成功结果后，如果下一段返回空内容或明确提示页码越界，表示提取完成。如果返回其他错误，不要假装已经读完；说明错误并处理实际原因。如果连续两段返回相同内容，停止并报告异常，不要无限循环。

提取完成后在最终报告里写明：使用的模式（精准 / 免 Token）、分段数；免 Token 模式下
图片、表格被占位符替代的段落列出页码范围，并附一句「精准模式可以改善这些段落的效果，
需要的话跟我说」——这是事后建议，不是提问，不要打断流程等回答。

## MinerU 排障

- API 请求失败但原因不清楚时，加 `-v` 查看请求和响应详情，例如 `mineru-open-api flash-extract "模组.pdf" -v`。
- `extract` 返回认证错误（HTTP 401 / `msgCode A0211`）时按「提取 PDF」节的降级规则处理；按「那一次提问」节的持久化流程更新 Token 后重跑失败段。
- 大文件处理超时时，将超时提高到 600 秒，例如追加 `--timeout 600`。
- 识别语言错误时，显式指定 `--language`，例如英文模组使用 `--language en`；中英混排保留默认 `ch`。
- 排障后只重试能被新信息合理修复的失败，不要无条件重复同一命令。

## 阅读并分章

你要阅读提取出的全部内容，并亲自判断章节边界。内容太长时按顺序分段阅读；先理解目录和全书主要结构，再确定最终文件名和章节范围。

- 结合目录和正文识别前言、主要章节与附录。
- 不要依据 Markdown 的 `#` 层级自动拆分，也不要另外编写标题解析程序。目录、页眉、场景标题和侧栏可能被 MinerU 识别成同级标题。
- 将场景、小节、侧栏、表格和怪物数据块保留在所属章节中。
- 使用模组中的实际章节名，并添加稳定的两位数字顺序前缀。
- 只修复你能确定的转录噪声；拿不准时保留提取结果，不补写缺失内容。
- 章节文件保存原文，不要用概述或摘要代替正文。

完成后按 `_原始解析` 的顺序复查一次，确认正文、侧栏、表格和附录都进入了正确章节，没有遗漏、重复或被摘要替换。

## 建立 Obsidian 导航

在 `00-目录.md` 中按阅读顺序列出所有章节，并使用从 Vault 根目录开始的完整 Wikilink，避免不同模组出现同名章节时产生歧义：

```markdown
- [[模组资料库/模组名/章节/01-前言|前言]]
- [[模组资料库/模组名/章节/02-第一章|第一章：标题]]
```

在每个章节顶部放置返回目录的链接，以及存在时的上一章和下一章链接。这样目录和章节之间都有显式导航，Obsidian 也会自动显示反向链接。

导入时只生成目录和章节。不要预先创建人物、地点、任务、遭遇或关系索引；用户需要时再根据章节内容生成。

交付前确认：

- 目录中的每个 Wikilink 都指向现有文件；
- 每个章节在目录中恰好出现一次；
- 每个章节都能回到目录；
- 前后章节链接与实际顺序一致。

## 回答模组问题

用户询问已经导入的模组时：

1. 先阅读该模组的 `00-目录.md`，再搜索全部章节。不要凭之前的会话记忆回答。
2. 阅读命中位置的上下文；需要时查看相邻章节。
3. 忠实引用或转述原文，说明来自哪个章节和小节。不要维护或报告 PDF 页码；DM 可以用回答中的原文搜索 PDF。
4. 明确区分模组原文、DM 笔记和你的推断。资料库没有答案时直接说明，不补写剧情或规则事实。

## 重新导入

重新导入已有模组时 0 次提问。先检查章节中是否有用户修改或 DM 笔记，一律先做时间戳
备份再更新，备份位置写进报告。不静默覆盖，也不把冲突处理抛给用户决定。

## 最终报告

写清：资料库绝对路径、使用的解析模式与分段数、本次安装指纹（如新装了 CLI）、备份
位置（如有）、质量备注（占位符段落与精准模式建议）。不要打印 Token、完整 CLI 配置或
任何凭据。
