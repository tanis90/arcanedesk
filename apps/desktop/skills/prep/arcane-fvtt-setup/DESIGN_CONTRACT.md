# arcane-fvtt-setup 设计契约

状态：草案，未定是否入库。约束对象：`SKILL.md` 与 `references/` 下各平台流程。
任何对本 skill 的修改若与本文冲突，先改本文再改 skill。

## 1. 用户身份

目标用户是不懂技术的小白 DM。

- 不知道 Node、SHA256、manifest、数据目录是什么，也没有能力判断它们。
- 不应被要求做任何技术判断。问小白技术问题等于转嫁责任，还会训练他无脑点"是"。
- 他能完成的是点击类操作：按图文指引复制链接、拖入文件、点弹窗、在网页里按步骤操作。

## 2. 用户交互预算

一次完整安装，用户交互点最多 3 个。每个都必须满足"只有他能做"或"一句话能答"。

| # | 交互点 | 性质 | 为什么必须是人 |
|---|--------|------|----------------|
| 1 | 提供 Foundry 付费工件：粘贴 timed URL 或拖入本地安装文件，agent 给图文指引。**交付物料即授权整个安装计划** | 只有他能做 | 付费软件，工件在用户账号里；agent 不代取、不猜 URL |
| 2 | 处理 OS 安全弹窗（UAC / Gatekeeper / 杀软），agent 提前预告、事后验收 | 只有他能做 | OS 信任边界，程序无法代点，也不准绕过 |
| 3 | 浏览器内收尾：EULA、license 激活、GM 登录，agent 在服务就绪后给精确步骤 | 只有他能做 | 法律同意与凭据，禁止代理 |

除此之外不得再有提问、确认或选择。新增任何用户交互前，先论证为什么不能归入这 3 点。

**计划声明（告知，不是交互）**：用户提出安装时、任何下载开始之前，agent 必须声明完整计划：
装什么（Foundry Core + Arcane Demo 环境：Demo world 及 profile 解析出的 system/modules）、
总下载量、解析后的准确目标路径，并附一句"不想装哪部分说一声"。
声明显示信息但不等待批准；用户交付物料即为对声明计划的授权。

## 3. 已拍板的默认项

- **Demo 环境默认安装**：用户说"帮我装 Foundry"即包含 Demo world 与其依赖的 system/modules，
  不在 Core 装完后单独询问。具体包集合由 `arcane-fvtt-mods` 的 `world-inspect` 实时解析，
  契约不钉死包清单。OSS 尚未发布 world 时不猜 URL，Core 安装仍可独立成功。
- **清单外第三方 mod：警告一次后照装**。用户要装 mod 时先查 arcane mirror 索引（OSS `index.json`）：
  mirror 已收录的按钉死流程直接装（固定 URL + SHA256 逐字节核对）；未收录的给一次大白话
  风险提示并取得确认——"这个不在 arcane mirror 选过的 mod 之内，安装可能产生不可知后果，
  确认要安装吗？"——同时附收录反馈渠道："如果你希望 arcane mirror 收录这个 mod，可以去
  官网 https://arcanedesk.bitterbebop.cn/ 反馈我们。"用户确认后即帮装，走 `arcane-fvtt-mods`
  的 install 流程（stage + `--accept-sha256`）；哈希由 agent 计算、核对、写进报告，
  但不再把 hex 串交给用户判断。此决策同时约束 `arcane-fvtt-mods` 的 install 流程：
  现行"展示计算哈希并再次确认"改为由上述一次风险提示覆盖。
- **mirror 有的内容全部走 mirror**：arcane mirror 已收录的内容（含 dnd5e）一律从 OSS 索引安装，
  验证基准只用索引声明的哈希，不再使用 `community-distribution.json` 中的 GitHub 上游条目做安装。
  禁止混链校验（从 mirror 下载却拿清单的 GitHub pin 验）——mirror ZIP 为重打包，哈希本就不同，
  混链必产生误报。清单 dnd5e 条目的处置（降级为出处/许可证记录或删除）在重写 skill 时一并处理。
  此链路的信任根是 mirror 收录时的收口与 OSS 账号安全；agent 侧机器校验不变：inspect 出计划哈希、
  stage 回传 `--expected-*`、helper 复读索引再下载验证、commit 前再验 staging，任一环节字节不符即拒绝。

## 4. 决策三分法

每个候选交互先归类：

- **A 类 法律/账户/系统边界**：必须人来（第 2 节 3 点）。agent 的职责是保姆化指引，把认知负担降到接近零。
- **B 类 信任决策**：全部合并进第 2 节的计划声明，随交互点 #1 一次展示，不单问。
- **C 类 技术细节**：不问。用默认值 + 可逆操作 + 事后报告替代询问。

## 5. C 类细节处理规则

| 原判断点 | 契约 |
|---|---|
| 每次下载前确认 | 用户交付物料（URL 或文件）即授权下载；与"用户要求安装即授权安装本身"同一原则 |
| Core/Data 目录选择 | 永远不问。默认值写死：Core = `…\runtime\foundry\<版本>`，Data = `…\runtime\foundry-data`（macOS 对应 userData 下）；计划声明与最终报告写清准确路径，附"想换位置告诉我"出口；迁移是独立指令，不是安装时的负担 |
| 覆盖/备份确认 | 自动备份即授权：发现冲突先时间戳备份再继续，报告备份位置。备份未成功不得继续 |
| 无预声明哈希时再确认一次 | 取消该交互。mirror 收录内容按钉死哈希直接装；未收录内容走第 3 节的一次风险提示；哈希只做机器校验与记录 |
| 单项超 250 MB 确认 | 体积并入计划声明，不单问 |
| macOS quarantine 说明 | 一句告知，不是等待批准的请求 |
| 便携模式相邻目录 | 用户不主动提，就永远用标准独立 Data 目录，不问 |

## 6. 路径表述纪律

既有 skill 用 `Data/systems` 这类简写指代安装位置，"Data"同时指外层数据目录和内层 `Data/`
子目录，已在真实会话中导致 system 装错层级（装到 `<数据目录>/systems` 而非
`<数据目录>/Data/systems`）。因此：

- skill 文本中所有路径一律用完整形态，如 `<数据目录>/Data/systems/<id>`、
  `<数据目录>/Data/worlds/<id>`，禁止 `Data/systems` 裸简写；首次出现处附目录树。
- agent 对用户输出和内部操作一律用解析后的绝对路径。
- 安装验收必须包含"从最终绝对路径回读 manifest（id/version）"。装错层级应当场验收失败，
  不允许拖到启动后扫描不到才发现。

## 7. 不可动摇的安全底线

交互精简不触碰以下纪律：

- 不代取 Foundry 付费工件、license，不代替用户同意 EULA。
- 不绕过 UAC / Gatekeeper / 安全软件；静默安装不得用于绕过提权。
- 不静默覆盖 Core、世界、用户数据；自动备份策略必须"备份成功才继续、备份位置写进报告"。
- 所有下载先落盘、验证，再按已声明的计划使用；不执行网络响应。
- 不打印 license key、完整 `options.json` 或凭据。
