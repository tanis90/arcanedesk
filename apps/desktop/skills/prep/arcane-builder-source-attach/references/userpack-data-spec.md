# 用户合集数据规范（DND 2014/2024 与 CoC）

本文件是 `arcane-builder-source-attach` 的随包参考，面向“先在世界里创作 Item，再接入车卡器”的流程。它描述工具与接收端实际消费的字段和验收边界；不需要也不假定作者另外持有仓库文件。

本文的“必须”是导入和车卡验收的硬约束；“建议”用于减少歧义、冲突和维护成本。所有内容按**纯数据用户包**处理，不附带可执行运行时。

## 1. 发布身份与 UUID

工具在规划阶段生成 canonical module dump，导入时统一改写到用户命名空间：

```text
发布包：Compendium.<moduleId>.<packName>.<documentType>.<documentId>
导入后：Compendium.user-<moduleId>.<packName>.<documentType>.<documentId>
```

- `moduleId` 必须稳定、唯一、小写；缺省 `homebrew-<campaignId>`。不要自带 `user-` 前缀，也不要复用 `dnd5e`、`brp`、`user-*` 或他人的模块 ID。
- 同合集后续发布保持相同 `moduleId`、pack 名和文档 `_id`。更换其中任何一个都会形成新的内容来源，而不是原包升级。
- 版本随内容变化递增；不要用 `latest`、`main`、`HEAD`。省略版本时由工具按同合集已有版本决定。
- 根 Item 使用世界 `Item.<id>` 传入；目标 UUID 由工具按相同 `_id` 与 pack 归属推导。不要手写 `Compendium.user-*`。

## 2. 文档共同约束

每个会被车卡器消费的文档必须：

- 有合法、稳定、非空的 16 位 `_id`，同 pack 内同 `_id` 不得对应不同内容；
- 有正确的 `name`、`type` 与目标系统的 `system` 数据；
- 使用目标系统当前版本支持的结构，不从其他系统或旧版本直接照搬；
- 中文内容至少让只懂中文的玩家能理解名称、描述和选择项；建议“中文 English”双语名称；
- 嵌入的 ActiveEffect / Item / 活动必须保持原生父子键位与效果键可解析；
- `type: "base"` 效果是嵌入数据，不应伪装成独立车卡选项；Folder 只是组织结构。

单条归一化文档必须小于 8 MiB；大型描述、base64 图片应改成正常素材文件引用。

## 3. DND 2014/2024：车卡器消费面

车卡器消费分两类：

- **直接目录条目**：玩家在职业、法术、专长、装备等列表中选择；
- **间接授予条目**：通过职业、子职业、种族、背景、装备组或 advancement 进入角色。

仅把文档做出来，不代表它会出现在目录或被正确授予。

| 内容 | 文档 `type` | 必需约束 |
| --- | --- | --- |
| 种族（2014）/ 物种（2024） | `race` | 原生种族数据、特性引用与对应版本字段完整 |
| 职业 | `class` | `system.identifier`、等级轨道、生命骰、施法与 advancement 完整 |
| 子职业 | `subclass` | 能被主职业的 Subclass advancement / 候选关系引用 |
| 背景 | `background` | 原生背景能力、熟练、特性、装备/财富数据完整 |
| 法术 | `spell` | 环阶、学派、施法时间、距离、持续、成分、描述与职业可用性数据完整 |
| 专长 | `feat` | 使用对应版本的 feat 类型/子类型，并进入实际读取的候选或授予关系 |
| 武器 | `weapon` | 原生伤害、属性、射程、价格、重量 |
| 护甲与通用装备 | `equipment` | 对应版本的装备分类、护甲、价格与属性 |
| 工具 | `tool` | 原生工具类型、熟练、价格与用途 |
| 消耗品 | `consumable` | 原生消耗品类型、数量、使用活动与价格 |
| 普通物品/战利品 | `loot` | 原生价格、重量、数量 |
| 容器 | `container` | 原生容量、价格与包含关系 |

`enchantment`、自定义 Item 类型或只在其他模块存在的类型，不因导入自动获得车卡支持。

### 3.1 五种 advancement 根 Item

“根 Item”指本次发布里玩家直接选择、并由工具向下推导依赖的文档。五种常见根：

1. **职业 `class`**：`system.identifier` 稳定；逐级 ItemGrant / ItemChoice / AbilityScoreImprovement / Subclass / ScaleValue 等 advancement 使用原生结构，`_id` 稳定；授予目标 UUID 能解析到本次合集文档或已显式声明的外部依赖。
2. **子职业 `subclass`**：通过主职业的 Subclass advancement 或候选关系被引用；解锁等级、特性等级和法术解锁等级与主职业一致。一次可传主职业 + 多个子职业。
3. **种族/物种 `race`**：原生特性引用和 advancement 关系完整；语言、技能、工具等选择项提供完整候选与数量。
4. **背景 `background`**：原生背景能力、熟练、特性、装备/财富数据完整；授予关系不要只写名称。
5. **专长 `feat`**：玩家直接选择的专长应使用 `system.type.value: "feat"` 并正确填写 `system.type.subtype`；职业/种族/背景特性通常也是 `type: "feat"` 但使用 `class` / `race` 等类型值并经 advancement 授予。不要把职业特性误做成只能在列表自选的通用专长。

旧式空 `type.value` 只有名称明确为 `feat` / `feats`（不是 `features`）的 pack 才按旧档规则识别，新内容不要依赖这条回退。规则版本使用目标版本原生 `system.source.rules`；留空按两版通用处理，不能拿它代替版本核对。

车卡器创建角色会记录来源 UUID，后续升级按来源回查职业。根文档缺少稳定 UUID，可能首次建卡成功后才在升级时暴露。

### 3.2 专长的两条路径

- **玩家直接选择的专长**：确认它属于当前车卡器支持的专长类别；`system.type`、先决条件、等级或 repeatable 等字段符合目标版本；被放入实际读取的专长候选来源；先决条件引用的职业、种族、其他专长或特性存在且标识一致。
- **职业/子职业/种族/背景特性**：由对应文档的 advancement 或其他原生授予关系进入角色。每个被引用特性必须实际存在并使用正确的 feat 类型/子类型；“额外专长”通过 ItemChoice / ItemGrant 再次授予。

2014 与 2024 的分类并不完全等价，应以目标版本的官方同类文档为模板，不能只改名称和描述。

### 3.3 法术与法术列表

- 法术要能被选择还要能被使用：原生活动、攻击/豁免、伤害、效果和持续时间字段必须合法。
- 法术与职业的关联使用目标版本原生 `system.classes` 字段。需要声明职业法术列表时，使用 `flags.<moduleId>.spellClasses`（或该版本支持的 `spellLists`），值为职业 `system.identifier` 小写数组；不能只靠名称相似或 pack 名推断。
- 自定义施法职业还要给出目标规则版的原生施法数量进阶，不能只写 `system.spellcasting.progression`。2014 使用 `ScaleValue` 的 `configuration.identifier: "cantrips-known"` / `"spells-known"` 与 `configuration.scale`，例如一级已知法术 6 写成 `{"1":{"value":6}}`；需要数量随等级变化时逐档给出，漏写会让对应法术配额变成 0。
- 按表准备法术使用特性上的 `flags.<moduleId>.preparedSpellTable`，候选、数量、过滤条件按接收端数据契约完整提供，不能只写布尔开关。
- 自动化只使用接收端已支持的 flag 和运行时协议；共享 DND 自动化数据按其约定命名，导入时由前端归一，不要并列写多份旧 flag。
- 动画所需绑定、投射物、图片或音视频素材必须随包并可解析。自定义脚本不会被本规范授予执行能力。
- 不要把“所有法术”自动公开给所有职业；没有结构化法术列表标注的法术只作为普通条目或依赖。

### 3.4 起始装备、装备组与财富

装备内容除了文档本身，还要检查职业/背景的 `system.startingEquipment` 或目标版本等效数据：

- 固定物品通过真实 UUID 链接到合集内 Item；
- `OR` 表示选择组，`AND` 表示组合；
- 子项 `group` 回链必须指向正确的容器 `_id`；
- 通用选择使用受支持的 `weapon`、`armor`、`focus`、`tool` 类别和 key；
- 数量、价格、容器包含与货币计算必须自洽；
- 需要玩家选择的分组不能静默默认取第一项；
- 装备组引用的物品必须随包提供或显式声明外部依赖。

武器、护甲、工具文档存在，不等于角色能自动获得起始装备；两条链都要验收。

## 4. CoC：技能与职业

| 内容 | 文档 `type` | 必需约束 |
| --- | --- | --- |
| 技能与专精 | `skill` | BRP 原生技能结构；基础值、技能族、专精父级和稳定标识正确 |
| 职业 | `occupation` | BRP 原生 occupation 结构；职业技能、职业点公式、信用评级与描述完整 |

- 一个逻辑 CoC 来源只能有**一个技能角色 pack 和一个职业角色 pack**；两类条目也可放在同一个 pack。不要拆成多个同角色 pack，也不要在同一战役同时启用多个 CoC 扩展模块作为同一合并来源。
- 职业技能引用必须指向实际存在且已启用的技能。技能族、专精父子关系和职业技能身份冲突必须显式处理，不能靠同名覆盖核心或其他作者的条目。
- 核心条目、扩展条目的 `brpid`、key、slug、文档 `_id` 等身份字段应与当前 BRP 数据契约一致；冲突时报错或明确排除，不能静默合并成另一张表。
- 武器、护甲与其他物品可以随合集导入供浏览/使用，但“导入成功”不等于进入 CoC 车卡器；只有已有明确消费链的类型才属于本规范承诺的建卡能力。

## 5. 引用闭包与外部依赖

发布包里所有本模块引用必须使用自己的 canonical moduleId：

```text
Compendium.alice-homebrew.spells.Item.xxxxxxxxxxxxxxxx
```

需要检查但不限于：`system.advancement`、`@UUID`/`@Embed`/富文本、`flags.dnd5e.sourceId`、`advancementOrigin`、`_stats.compendiumSource`、效果/活动/召唤/装备与特性来源字段。

优先制作自包含合集。确需外部依赖时：

- 依赖必须是接收方已启用且可获得的 Compendium；
- 不把作者本机的私有包、临时目录或其他玩家不可见内容当作依赖；
- 不依赖导入器自动修复任意外部 UUID。

工具会检查本次 dump 内部的 canonical 引用闭包，并拒绝残留的世界 `@UUID[Item.<id>]`；外部 Compendium 依赖由规划阶段验证并原样保留。

## 6. 素材

- 图片、token、动画和音视频随包携带；
- 使用 `modules/<moduleId>/assets/...` 或导入器支持的包内相对路径；
- 不使用作者机器绝对路径、临时签名 URL、私有地址或无法长期访问的外链；
- 文件名、目录和文档引用大小写一致；
- 第三方素材附来源、作者和许可证信息；
- 内置 `systems/packages` 引用不重复上传；远端素材由 play 页在规划时读取字节并以有界传输交付，模型永远看不到字节或签名 query。

规模上限：20 个根 Item、200 个依赖文档、依赖深度 8、单文档 8 MiB、素材总量 32 MiB。超限时不要自造第二套长程通道；改用现有合集 ZIP 导入流程或先削减内容。

## 7. 更新、替换与兼容边界

- 相同 `moduleId` 的再次发布用于更新同一用户包；不同 `moduleId` 会建立另一个来源。
- 工具按目标 pack 增量合并：本次同 `_id` 内容覆盖旧条目，未涉及的旧条目与旧 pack 保留；首版没有条目删除。
- 更新包不会自动重写已经取用到世界的角色快照，也不会自动迁移旧来源 UUID。
- 不承诺旧内测包或旧角色向新自定义包的自动兼容。
- 作者必须自行确认规则文本、译文、图片和其他素材的再分发权利。

## 8. 发布前检查

### 8.1 结构

- [ ] 只有一个稳定 `moduleId`，同合集后续版本保持一致；
- [ ] 根 Item 类型合法，`_id` 合法且无冲突；
- [ ] pack 归属与文档类型、系统一致；
- [ ] 不依赖脚本、宏或运行时入口；
- [ ] 单条文档小于 8 MiB，素材总量在 32 MiB 内。

### 8.2 引用

- [ ] advancement、特性、专长、法术、装备组引用闭合；
- [ ] 包内 UUID 使用自己的 canonical moduleId；
- [ ] 不存在残留世界 UUID、作者本机路径或临时签名 URL；
- [ ] 图片、token、动画和音视频引用有实际文件。

### 8.3 DND 真机验收（工具不代做）

- [ ] 另一 DM 在干净用户库导入成功；
- [ ] 玩家无需导入即可看到并选择种族、职业、子职业和背景；
- [ ] 专长列表与专长授予都正确，不只验证职业特性；
- [ ] 法术候选、详情、职业限制和升级新增法术正确；
- [ ] 起始装备、装备组选择、数量和财富正确；
- [ ] 新角色至少升一级，特性、专长、子职业和 advancement 无断链；
- [ ] 需要自动化/动画的条目完成真实结算验收。

### 8.4 CoC 真机验收（工具不代做）

- [ ] 自定义 moduleId 和 pack 名下技能、职业均可发现；
- [ ] 职业技能、职业点、信用评级和专精关系正确；
- [ ] 缺包、空包、类型错误和身份冲突都有明确错误；
- [ ] 核心与自定义内容不会静默重复或互相覆盖。

工具回执能证明的是：规划、导入、选包、用户包注册、根 UUID 解析、身份候选、法术表标注与内部引用闭包。真实玩家建卡、升级、战斗和跨端刷新必须另行验收；没有执行就写“未执行”，不要把世界 Item 创建成功或合集导入成功当成玩家可用。
